# Delta

A git GUI in Go with Qt 6 through the miqt bindings, modelled on `git gui` and `gitk`. `plan.txt` is the original brief. `../apemail` is the reference for the toolbar, icons, about box, colours, the settings dialog's frames and keeping to one copy, `../reghead` for the pane splitters and the size of the change circles, and `../prism` for the table of colours and the themes: use them as references, don't copy from them.

## Rules

* After every change run `make build` and `make install`, and `make vet` and `make test` when code changed. `staticcheck ./...` and `deadcode -test ./...` must be clean, and `gofmt -l .` empty. Run `make race` too when what goes to the background changes: only the race detector finds a value touched from both sides.
* Keep this file and README.md up to date with every change.
* Every bug found gets a unit test that fails without the fix, so that it can't come back. Check that it does fail without it.
* Don't commit or stage; the user does that. Move and delete files without `git mv` or `git rm`.
* miqt comes from `github.com/mappu/miqt`, at the latest commit of its master branch (`go get github.com/mappu/miqt@master`), not its last tag: "latest" means master. No `replace` directives or local dependencies.
* Delete only what `qt.New…` makes. A value miqt returns by value (a size, a font, a palette) is freed by its finalizer: deleting it frees it twice, which crashes only when the collector runs. Keep it alive with `runtime.KeepAlive` while what it gave is used.
* Qt is only touched on the main thread. Anything that runs git in the background comes back through `mainthread.Start`, and tests use `mainthread.Wait`.
* Test it yourself, offscreen. Never open windows on the user's desktop, inject input, or ask the user to try something; say plainly what could not be checked (a real drag, Wayland's focus) instead.

## Packaging

`packaging/` and `.github/workflows/` are adapted from `../prism`: an AppImage built in an Ubuntu 22.04 container with Qt's own 6.9.3, and a macOS app for Apple Silicon with Homebrew's qtbase, both on `v` tags or by hand.

The icon (three green slanted bars making a triangle) is `internal/appicon/appicon.png`, a 256×256 PNG embedded by the `appicon` package, as apemail's is: the window's, the about box's, and the desktop entry's (installed as a 256 pixel icon). To change it, replace the file with one of the same size (`TestPNG` checks) and run `make icons`, which draws the macOS app's, `packaging/macos/delta.png`, from it within Apple's margin (`drawMacIcon`); `TestPackagedIconsAreCurrent` fails until that is done. The AppImage copies the icon as it is (`appimage.sh`). `make screenshots` redraws `docs/changes.png` and `docs/history.png`, in the light theme (the user's choice): any screenshot added to the README is too. `TestPackagedEntryAgrees` keeps `packaging/delta.desktop` in step with the entry written at start.

## Layout

* `internal/git`: runs the git command line (`git.go`; `rebase.go` for interactive rebases; `tip.go` reads the last two commits for `quickfix.go`, quick fixes, and `uncommit.go`; `finish.go` for finishing a branch; `snapshot.go`, everything a rescan reads; `parallel.go`, running reads at once). No Qt. Tests use real temporary repositories.
* `internal/diff`: turns git's diff output into what is shown, and what each line is. No Qt.
* `internal/graph`: lays out commits in lanes for the graph. No Qt.
* `internal/settings`: the JSON settings, with defaults for unusable values (`settings.go`), and Solarized's colours (`solarized.go`). No Qt.
* `internal/appicon`: the program's icon, embedded. No Qt.
* `internal/desktop`: writes the Linux desktop entry and icon, at every start, only when they differ. No Qt.
* `internal/instance`: keeps to one copy running, as `../apemail` does. No Qt.
* `internal/atomicfile`: replaces a file whole, through a temporary file, for the settings and the desktop entry. No Qt.
* `internal/ui`, tested with the offscreen platform:
  * `window.go`: the window, its menus and toolbar, the status bar, reading the status, and the settings. `repobar.go`: the dropdowns of repositories and branches at the toolbar's right.
  * `operations.go`: every git command the menus and buttons run, and the questions before them.
  * `changesview.go`: the changes, as `git gui` has them. `historyview.go`: the history, as `gitk` has it, its loading and its commits' context menu. `graphcolumn.go` paints its graph. `diffview.go` shows a diff in either.
  * `rebasedialog.go`: the plan of an interactive rebase.
  * `dialogs.go`: the small form dialogs and questions, and the Checkout dialog. `settingsdialog.go`, `about.go`.
  * `iconengine.go`: icons drawn each time they are shown (`paintedIcon`). `toolicons.go`: the toolbar's icons. `changeicons.go`: the circles of changed files. `progress.go`: the progress bar, the sign of work. `icon.go`: the program's icon.
  * `theme.go`, and `widgets.go` for what several share: pane splitters and their handles, headings, the pages' margin, the code's font, the rows of changed files, and fitting a dialog to its contents (`fitHeight`).

## Behaviour to keep

### Git

* Git runs with `--literal-pathspecs`, `GIT_TERMINAL_PROMPT=0`, `GIT_EDITOR=true`, `GIT_MERGE_AUTOEDIT=no` and in a new session (`Setsid`), so it can't hang waiting on a terminal, and with `GIT_OPTIONAL_LOCKS=0`, so that its background reads don't get in the way of other git commands. `Setsid` is why this builds for Linux and macOS but not Windows.
* `Window.background` runs one changing command at a time off the main thread, with the actions disabled, then rescans. `Window.run` is that, telling of any failure; deleting a branch uses `background` itself, as a refusal from git becomes a question. Rescans, diffs and the history run in the background too, and an answer that isn't to the latest request is dropped.
* The main thread runs no git but a new branch name's validity, checked as it is typed (`ValidBranchName`). What a dialog needs first (branches, remotes, stashes, a remote's URL, a rebase's commits) is read in the background by `readFirst`, which opens the dialog when it is back: one at a time (`Window.reading`, so a shortcut pressed twice opens one), dropped if another repository is open or a command has started by then, a failure told of under the dialog's title (`TestReadFirst`, `TestReadFirstDropped`).
* Repositories are looked for in the background (`findRepository`, which runs `git.Open`), on starting, from File > Open, the bar and `Activate`: only the latest asked for is opened, and opening one at once (`openRepository`, which tests use, and `useRepository`) drops any still being looked for (`Window.opens`, `TestLatestRepositoryOpens`). `Window.finding` counts those being looked for; test windows wait for it to be 0.
* Reads that don't depend on each other run at once, each goroutine writing only its own variables, read once all are back (`together`): the status (its porcelain, `MERGE_HEAD` and the rebase's state), a commit's detail (its files, header and diff), the uncommitted row's (its files, diff and status, then the untracked files' diffs, `readers` at a time with `each`, in their order, stopping at a cut as one after another would, `TestUntrackedDiffsStopAtTheCut`), the history's log and status (`readHistory`), and a rescan's status, branches, stashes, last commits and merge message (`Repo.Snapshot`, shown by `Window.applySnapshot`). Of reads at once that fail, the error is the first in the order they would have run (`firstError`).
* What touches no Qt is worked out in the background with what it shows: diffs are parsed there (`diff.Parse`, then `diffView.showParsed`), and the history's pages are laid out there with their rows' texts (`layOutPage`, a `historyPage`). The next page is laid out in a copy of the layout (`graph.Layout.Clone`), which replaces it once back, as anything that changes the layout meanwhile also drops that answer (`TestHistoryPagesJoinUp`, `TestHistoryPageDroppedAfterReload`). Only filling and painting widgets stays on the main thread.
* Every piece of background work calls `beginWork` before it goes and `endWork` first thing when it comes back, its answer used or dropped, so that they always pair (`TestWorkPairs`); Checkout's fetch does so from its goroutine through `mainthread`.
* Status comes from `git status --porcelain=v2 --branch -z`, with a merge and a rebase in progress (`Status.Merging`, `Status.Rebasing`, read from `rebase-merge` or `rebase-apply`). Unstaging always names paths, as a `git reset` without any would abandon a merge in progress. A status line's old path goes only on the side that renamed or copied the file (`sideOf`), as staging names it to git.
* Diffs are read up to `git.MaxDiff`, and nothing follows one that was cut off. All patches are asked for with `git.patchOptions`, which `diff.Parse` relies on. It drops each file's header (`diff`, `index`, `---`, `+++`, new and deleted file modes, similarity), keeping what is news (renames, mode changes, binary). In the history a bold file name replaces it (`diffView.titles`), which file jumping uses (`Parsed.Files`). It also makes sure the text has exactly one block per line, which `diffView.paint` relies on.
* Stashes (`git.StashChanges`, `Stashes`, `ApplyStash`, `DropStash`) run without `--literal-pathspecs` (`runStash`, `commandPaths`), as with it `git stash push --include-untracked` saves untracked files but leaves them; they name no paths. Apply and Pop use `--index`. A failure holds `ErrStashConflicts` (a `CONFLICT (` line: applied with conflicts, the stash kept even by a pop) or `ErrStashIndex` ("conflicts in index": nothing changed). How many stashes there are is read with every rescan (`Window.stashes`).
* The last commit and the one before it are read once with every rescan (`git.ReadTip`), and give both what a quick fix would do (`Tip.QuickFix`, kept as `Window.quickFix`) and whether the last commit can be uncommitted (`Tip.UncommitRefused`, kept as `Window.canUncommit`).
* A quick fix (`Tip.QuickFix`, then `RunQuickFix`) folds every change not committed, untracked files included (`add --all`), into the last commit with `commit --amend --no-edit`; with none, it folds the last commit into the one before it without a rebase: `commit-tree` of HEAD's files with the parents, message (exactly, from `cat-file`) and author of the one before, then `update-ref` from the planned HEAD only, so that nothing done since is lost. Neither can conflict. There is none without commits, nor a fold of or into a merge, nor of a root commit.
* Uncommit (`git.Uncommit`) is `reset --mixed` to the last commit's parent, so that its changes, and any staged before, are left unstaged as if new; the first commit of a branch is taken back to none (`update-ref -d HEAD` from it only, then `read-tree --empty`), its files untracked. A merge is refused (`Tip.UncommitRefused`), as taking it back would mix the branch merged in with the changes.
* Finishing a branch (`git.FinishBranch`) checks out the main branch (`MainBranch`: main, or else master), pulls into it, and deletes the branch with `-d`, stopping at the first step that fails, so that the branch goes only once main is up to date; git refusing to delete it, as not merged, holds `ErrBranchKept`.
* Force push is `--force-with-lease` and always asks first. Discard All Changes is `git reset --hard HEAD` then `git clean -f -d` (`git.DiscardChanges`; `read-tree --empty` on a branch with no commits), keeping ignored files and commits and abandoning a merge.

### The window

* One copy runs for each user (`internal/instance`, on apemail's design): the one that runs holds a `flock` on `delta.lock` and listens on `delta.sock` beside it, in `XDG_RUNTIME_DIR` or else a folder of the user's own in the temporary folder (`Dir`). One started while it runs sends it a `Request`, a line of JSON, and leaves: the desktop's activation token, read before Qt starts, and the folder it would have opened, the one named made absolute (`Named`) or else the folder it was started in. `main.go` claims once Qt has taken its own arguments, before anything else. `Window.Activate` unminimises, raises and activates the window, the token in `XDG_ACTIVATION_TOKEN` for Qt under Wayland, then opens the folder's repository unless it is the one open, not while a command runs; a folder named that is in no repository is told of, one started in is ignored. One that holds the lock but doesn't answer within `answerWait` makes the new copy leave with an error; a lock that can't be had at all lets it run. Only the holder of the lock removes a socket left by a copy that died.
* There are no tabs. The window shows the changes, or the history in their place while History is on (`views`, a stacked widget; `setHistoryShown`, `historyShown`). It always starts on the changes, whatever the repository holds (the user's choice). History is a checkable action, the toolbar's History and the Branch menu's Show History on Ctrl+H.
* Under the menus is a toolbar the size of apemail's (`makeToolBar`: 32 pixel icons, text under them, not movable): Open, a separator, New Branch, Checkout, Finish, a separator, Rescan, a separator, Pull, Push, a separator, History. It has no Stage or Delete button (the user's choice). Each button is at least `toolButtonWidth` wide, so that short names are not thin, and has no tooltip: Qt gives a button its action's name as one whatever is set, so an event filter takes the tooltip event. Its buttons are the menus' own actions, with their icon text set to drop the ellipsis, so that they are enabled alike, but for Push, below.
* The toolbar's icons are drawn in code in apemail's style (`toolicons.go`: outlines on a grid of 24, 1.5 wide, round ends and joins, in the palette's text colour, disabled text where disabled), through `paintedIcon`, so that they follow the theme and Qt's SVG module is not needed.
* At the toolbar's right are the dropdowns, in one widget (`repoBar`) that takes up the room beyond the buttons, with a stretch of its own pushing them right, so that Qt narrows it before putting it in the toolbar's menu of what does not fit. Each dropdown is as wide as its longest name, from `repoComboLeast` to `repoComboMost`, where names are cut short, and narrows to the least where there is no room; both are on show at the least in a window of the default width, 1320 (`TestRepoBarInToolbar`, `TestRepoComboWidth`). Repository is a dropdown of every repository opened (`Settings.Repositories`), by the name of its folder only (the user's choice), in order of that ignoring case and then of the whole path (`byFolder`), each one's whole path its tooltip; then Branch, a dropdown of the local branches (`byName`), the current one chosen, or none on a detached HEAD, and listed even before the first commit when git lists none. They act on `OnActivated` only, so that filling them does nothing: choosing a repository opens it (one that can't be is told of, and the one open chosen again), and choosing a branch checks it out. The branches are read with the status on every rescan.
* There is no spinner in the toolbar (the user's choice). Under it, the width of the window, is a progress bar (`progress.go`), `progressHeight` high, busy rather than counting, with no text. It is painted here, not by the style, as Fusion's busy bar is a still block of colour: a segment in `ProgressColour` sweeping across a faint track in the theme's colours (`progress.chunk`). It shows once background work has gone on for `progressDelay`, so that quick work does not flicker, and goes when the count is back to 0. It keeps its room while hidden, so that the panes don't move as it shows and goes (`TestProgress`).
* The status bar has a size grip and all its text at the left, at 50% opacity: the branch, then the last message, in labels of their own (`Window.say`). Don't use `ShowMessage`, which hides widgets beside it, or `AddPermanentWidget`, which goes on the right. A rebase in progress shows how far it has got there.
* Pane headings are bold (`heading`), and splitter handles are made through `OnCreateHandle` to paint only a row of grip dots, as `../reghead` does (`newPaneSplitter`).
* On starting, the repository opened is the one named on the command line, or else the one the current folder is in, or else the one last opened (`Settings.LastRepository`, the user's choice), or else none, waiting for File > Open Repository. One last opened that can't be opened again is said so in the status bar, without a dialog. An older settings file's `repository` is ignored. On opening any repository, the first unstaged file, if there is one, is chosen once its status is read, showing its diff (`chooseFirst`, `chooseFirstFile`), but not on later rescans, and not if a file has been chosen by then. Every repository opened, starting in one included, is added to `Settings.Repositories` by its top folder, made `LastRepository`, and saved at once (`Settings.Remember`, which keeps each absolute path once, moving one opened again to the end as the one opened last; `Load` drops duplicates and relative paths too). At most `RepositoryLimit` are kept (20 by default, 1 to 100, a setting), those opened longest ago going first; lowering it trims the list and the bar at once (`LimitRepositories`).
* Window size, maximized state and the three splitters are saved on close, and the rebase dialog's size whenever it closes. Pane sizes are applied after the window is shown. A window must not be deleted while a background command may still answer to it, so tests close windows without deleting them.

### The changes

* A changed file in a list is its path with a circle for what happened to it (`changeIcon`), in place of git's letter: `changeDotSize` (12, as reghead's dots) wide, an outline in its colour `changeOutline` (2) pixels wide with a wash of it (`changeFill`) inside, as apemail's folders are. The colours are the settings' `ChangeColours`, by default Solarized's (blue modified, green added, red deleted, violet renamed, cyan copied, yellow type changed, orange in conflict, and its base0 grey untracked), the same in every theme (the user's choice), and kept on a selected row; the circles are painted from `changeColours`, by code, each time they are shown. The history's files say it in words in a tooltip (`explain`); the staged and unstaged lists have no tooltips (the user's choice). The first row of the history's files, the message, has a blank of the same size.
* In the file lists, ctrl and shift select several files. Dragging keeps one file selected, moving with the pointer, so each is shown in the diff in turn (`newFileList`). Only one list has a selection at a time.
* The Stage Changes button beside the message (`changesView.stage`) stages everything listed, and is Unstage Changes when everything is staged (`allStaged`, kept as `unstaging`, not read back from a label). The Stage Changes menu item only stages; Stage Selected (Ctrl+S) and double-click stage only those chosen.
* Both Push buttons are `pushButton`, which forces while Force push is ticked; the Remote menu's Push, on Ctrl+P, never forces (the user's choice), and its Force Push… always does. The toolbar's Push is a split button (`MenuButtonPopup`) whose own menu, not the Remote menu, has a checkable Force push option (`forceToggle`), ticked along with the checkbox either way. While ticked, both Push buttons say Force Push. A successful push clears them all. Whether it is ticked is saved on closing (`ForcePush`) and ticked again on starting, once the window is joined up so that the option and buttons follow.
* The Stash menu, between Commit and Remote: Stash Changes… on Ctrl+Shift+Z (`newStashDialog`: a message, which may be empty, and Include untracked files, unticked), Apply Stash…, Pop Stash…, a separator, Drop Stash…, which asks first. A stash is chosen from a list, newest first (`askStash`). Stash Changes is enabled with something to stash, the others with a stash, and none during a merge or rebase. A stash applied with conflicts says so in the status bar (`stashConflictText`), not in an error; one whose index can't be put back asks whether to apply it with everything unstaged (`applyStash`); any other refusal shows git's error. Delta neither suggests nor requires a clean tree to apply onto (not chosen).
* Quick Fix… is in the Commit menu after Commit and Uncommit and a separator, on Ctrl+Shift+Q (the user's choice), with no button beside the message (the user's choice). It always asks first, No being the default, as it rewrites the branch (the user's choice), naming the commits, and saying when what it rewrites has been pushed, so that a force push will be needed (`quickFixQuestion`: the last commit for an amend, the one before too for a fold, by `Ahead`, through `pushedNote`, which Uncommit's question shares). It is enabled only when the plan allows one, and not during a merge or rebase. Commit hooks are not considered (the user's choice).
* Uncommit… is in the Commit menu straight after Commit, on Ctrl+Shift+Return (the user's choice), and then a separator before Quick Fix…. It always asks first, No being the default (the user's choice), naming the commit and saying when it has been pushed, so that a force push will be needed (`uncommitQuestion`). It is enabled only when the last commit can be taken back, and not during a merge or rebase.
* Finish Branch… (the user's "git done") is in the Branch menu after Checkout, with no shortcut, and on the toolbar after Checkout as Finish, with a flag (`finishShape`). It is enabled on any branch but the main one, which must be among the local branches read with every rescan (`Window.localBranches`), and not during a merge or rebase. With changes not committed it says to commit or stash them first and does nothing; otherwise it asks first, then runs in the background. A branch git won't delete is kept, on main, and it asks whether to delete it anyway, as Delete Branch does.
* Discard All Changes, in the Branch menu on Ctrl+Shift+D, always asks first, No being the default, counting files put back and new files (untracked or newly staged) deleted. It is enabled only with something to discard, and not during a rebase, which has Abort Rebase.

### The history

* It is like gitk: the commits of HEAD above, in `--topo-order`, as the graph needs every commit before its parents, and the chosen commit's files beside its whole diff below. They are read `pageSize` at a time, from the settings' `HistoryPageSize` (500 by default, 50 to 10000, taking effect from the next read), and more on scrolling to the end. Choosing a file scrolls to its name in the diff, relying on `git diff-tree --name-status` and `-p` listing files in the same order. Merges are diffed against their first parent.
* It reads only while on show: a rescan marks it stale (`markHistoryStale`), and it reloads on being shown. Its panes get their sizes when first shown (`historyView.sized`), and are saved only if they have been.
* While there is anything uncommitted, the first row is a stand-in commit (`git.UncommittedCommit`), whose parent is HEAD so that the graph joins up. It is in `historyView.list`, but read commits are counted without it (`committed`). `CommitDetail` shows it as everything since HEAD plus untracked files. It changes without its row changing, so it is read again on every rescan, keeping its scroll position.
* The graph is a column of the commit list, painted by an item delegate (`graphColumn`) from `graph.Layout`'s rows: only rows on show are painted, and it scrolls with the list. The layout is fed a page at a time. Each row's bottom edges must meet the next row's top edges, which `TestRowsJoinUp` checks on random histories. Changing lanes is an S curve leaving and arriving upright, so that lines run on smoothly between rows. The column is as wide as the lanes need, up to `graphMost`. A first parent already waited for in a lane to the right doesn't step over to it: its own lane waits too, and they meet at the parent, in the leftmost, so the graph doesn't wander right (`TestDoesNotWanderRight`).

### Interactive rebase

* It starts from a commit's context menu in the history, Rebase from here… (`commitMenu`), never the uncommitted row, and only on a clean work tree with no merge or rebase going. It covers that commit up to HEAD (`git.RebaseCommits`, which refuses a range holding a merge).
* The dialog (`rebaseDialog`) edits the plan: a row per commit, oldest first, each with its own combo of actions, in the order Pick, Fixup, Reword, Edit, Squash, Drop (`git.Actions`). A combo is an item widget; the wheel changes it only once it has focus, so that it scrolls the list; focusing or choosing in it makes its row the only one chosen (`chooseOnly`), so that the message below is that commit's. Below the list is only the chosen commit's message, full width, with no diff. The dialog has no keyboard shortcuts (the user's choice).
* The message is enabled only for a commit reworded, so that it is visibly greyed otherwise. Reword puts the cursor in it once the popup has closed (`editMessage`), and for a second after sends the focus back to it if it lands on the list or a combo (`reclaimFocus`), as on Wayland closing the popup puts the focus on the list later still.
* Rows are only dragged into order (`moved`). Qt only draws where a drag would go: the drop is handled in `dropAt` and ignored, so that Qt moves no rows, as it would delete the combos of rows it moved. Rows stay in place while the steps shown on them change. Qt delivers no drag events sent by hand, so tests call `dropAt`.
* Long messages are cut in the list (`subjectWidth`) and tooltips (`excerpt`), and shown whole below. The dialog's size is saved (`RebaseWidth`, `RebaseHeight`, 0 until it is first closed, when it opens at four fifths of the window). It is marked `finished` before it is deleted, so that a timer firing late does nothing.
* Git is given the plan through `GIT_SEQUENCE_EDITOR`, a `cp` of a temporary file. Reword is a pick then an `exec` that amends with the new message, a line at a time through `printf`, each quoted for the shell (`git.todo`), as git would otherwise want an editor. Squash keeps both messages as git joins them, as there is no editor.
* A stop is told of by `Window.rebaseStep` and handled from the Branch menu: Continue Rebase amends what is staged into a commit stopped at to edit, then continues; Skip Commit; Abort Rebase.

### Dialogs

* No two of the window's actions share a shortcut (`TestShortcuts`).

* Form dialogs' fields grow to the dialog's width (`AllNonFixedFieldsGrow`), as some styles keep them narrow, and the first field of text has the focus when one is shown (`formDialog.firstText`), as it would otherwise go to OK, made first, unless `formDialog.focus` names another. A dialog answered is marked `finished`, so that what comes back from the background later touches nothing.
* New Branch (`newBranchDialog`) corrects the name on OK (`git.SanitiseBranchName`: white space to a hyphen, what git refuses taken out, "@" alone dropped as git takes it for HEAD), with OK enabled while the corrected name is one git takes (`TestSanitisedNamesAreValid`, `TestNewBranchName`).
* Checkout (`newCheckoutDialog`) offers every local branch, in order of name ignoring case (`byName`), with the current one chosen and its list focused; OK is disabled while the current one is chosen, as there is nothing to do. Its Include remote branches checkbox, unticked to start with, adds the remote ones after them, in order too. Ticking it the first time fetches (`git fetch --all`, through `checkoutFetch`) in the background, with the list and OK disabled and Fetching… said; a failed fetch says why and lists those already known. What the fetch notes for the window, that it fetched and the count of work, it notes on the main thread (`TestCheckoutFetch`, under `make race`). The branch chosen is kept while it is still listed, or else the current one is chosen again. A cancelled dialog that fetched rescans. A remote branch is checked out as a new local branch tracking it.

### Look and settings

* Every colour the program gives itself is Solarized's by default (the user's choice), and is a setting: the diff's (`AddedColour`, `RemovedColour`, `HunkColour`), the change circles (`ChangeColours`, whose `Fields` give them in one order, for normalising and the dialog alike, `TestChangeColourFields`) and the progress bar's segment (`ProgressColour`). The graph's lanes are Solarized's eight accents, fixed in code (`graphColours`), not a setting (the user's choice). Solarized's sixteen colours are named once, in `internal/settings/solarized.go`, and the defaults are made of them (`TestColoursAreSolarized`). `Window.applyColours`, at start and on every change of the settings, is the one place they are put into effect: the diffs, the circles, painting the file lists again, and the progress bar. What is drawn in the palette's colours (text, icons, grips, the progress bar's track) follows the theme.
* Never change the themes or their palettes (`theme.go`) unless asked to by name: "Solarized throughout" does not include them (the user's choice).
* Themes: light and dark are Fusion with our own palette; following the system restores the desktop's style and an empty palette. `applyTheme` is not called at startup when following the system.
* Diffs colour text, not backgrounds (the user's choice): added and removed lines take their colours as they are, through char formats (`diffView.paint`), and a hunk's `@@` range is in the Hunk headers colour, any text after it the normal colour. Nothing in a diff has a background. The default colours are Solarized's green, red and base0 grey (`DefaultAdded`, `DefaultRemoved`, `DefaultHunk`), as the change circles are.
* The settings dialog is laid out as `../apemail`'s (the user's choice): two tabs, General first, with Repositories above History, then User interface, with Appearance and Colours, of frames (`QGroupBox`, `settingsDialog.section`), each titled, with a wrapped note on what it is for, but for Appearance and Colours, which have none (the user's choice), and then its fields, labelled with a colon. Appearance has Theme and Code font (one row as apemail has it: any font of the system, no monospaced filter as the user wants any, the size inline, and a Default button); History has the commits read at a time ("Commits:"), its note only "The history is read this many commits at a time." (the user's choice); Repositories, its note "The repositories opened are remembered, up to this many.", has how many are remembered ("Remembered:"); Colours has the table of colours, Name and Colour as `../prism` has it, with bold section rows across it (Diff, Changed files from `changeNames`, in the order of `ChangeColours.Fields`, Progress bar; the graph's lanes are not in it, the user's choice), and Use Default Colours under it (the user's choice: a table, not a tab or forms of its own). A colour button is filled with its colour, named in Solarized's darkest or lightest, and has a border of its own in its style sheet, as Fusion otherwise shades a style sheet's background paler (`TestColourButtonIsItsColour`). The notes wrap onto more lines than Qt allows for, so the dialog is given the height its contents need at its width, and no less (`fitHeight`, `TestSettingsDialogFits`). The code's font and size (`CodeFont`, `CodeFontSize`) apply to both diffs and the commit message; empty or 0 follows the system's fixed width font.
* The about box's title is as apemail's (`newAboutTitle`): the name in bold at `titleScale`, with the version to its right on the same baseline at `versionScale` and `versionOpacity`, as the release it is or follows (`release`: v1.2.4-0.… is shown as v1.2.3), or dev. The box is fitted to the height its contents need at its width (`fitHeight`), as apemail's is, as Qt's own height leaves a gap above the licences.
