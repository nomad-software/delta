# Delta

A git GUI in Go with Qt 6 through the miqt bindings, modelled on `git gui`. `plan.txt` is the original brief. `../prism` is a reference for the look of the settings, about box and themes: use it as a reference, don't copy from it.

## Rules

* After every change run `make build` and `make install`, and `make vet` and `make test` when code changed. `staticcheck ./...` and `deadcode -test ./...` must be clean.
* Keep this file and README.md up to date with every change.
* Every bug found gets a unit test that fails without the fix, so that it can't come back.
* Don't commit; the user does that.
* miqt comes from `github.com/mappu/miqt`, at the latest commit of its master branch (`go get github.com/mappu/miqt@master`), not its last tag: "latest" means master. No `replace` directives or local dependencies.
* Delete only what `qt.New…` makes. A value miqt returns by value is freed by its finalizer.
* Qt is only touched on the main thread. Anything that runs git in the background comes back through `mainthread.Start`, and tests use `mainthread.Wait`.

## Packaging

`packaging/` and `.github/workflows/` are adapted from `../prism`: an AppImage built in an Ubuntu 22.04 container with Qt's own 6.9.3, and a macOS app for Apple Silicon with Homebrew's qtbase, both on `v` tags or by hand. The icon (a dark triangle on a sun) is `internal/appicon/appicon.png`, a 256×256 PNG embedded by the `appicon` package, as apemail's is, for the window, the about box and the desktop entry (installed as a 256 pixel icon, the 128 pixel one of old being removed). To change it, replace the file with one of the same size (`TestPNG` checks) and run `make icons`, which draws the macOS app's, `packaging/macos/delta.png`, from it within Apple's margin (`drawMacIcon`); `TestPackagedIconsAreCurrent` says when that is needed. The AppImage copies it as it is (`appimage.sh`). `make screenshots` redraws `docs/`. `TestPackagedEntryAgrees` `TestPackagedEntryAgrees` keeps `packaging/delta.desktop` in step with what is written at start.

## Layout

* `internal/git`: runs the git command line (`rebase.go` for interactive rebases). No Qt. Tests use real temporary repositories.
* `internal/diff`: turns git's diff output into what is shown, and what each line is. No Qt.
* `internal/graph`: lays out commits in lanes for the graph. No Qt.
* `internal/appicon`: the program's icon, embedded. No Qt.
* `internal/desktop`: writes the Linux desktop entry and icon, at every start, only when they differ. No Qt.
* `internal/settings`: the JSON settings, with defaults for unusable values. No Qt.
* `internal/atomicfile`: replaces a file whole, through a temporary file, for the settings and the desktop entry. No Qt.
* `internal/ui`: `window.go` (the window, its menus, reading status and settings), `operations.go` (every git command the menus and buttons run, and the questions before them), `branchtab.go` (the changes' widgets), `historytab.go` (the history, its loading, its commits' context menu and the History button's showing it included), `rebasedialog.go` (the plan of an interactive rebase), `graphcolumn.go` (paints the graph), `diffview.go`, `settingsdialog.go`, `about.go`, `theme.go`, `dialogs.go`, `icon.go`, `toolicons.go` (the toolbar's icons), `spinner.go` (the toolbar's sign of work), `changeicons.go` (the circles of changed files), `widgets.go` (what several of those share: pane splitters and their handles, headings, the code's font, and the text of a change in a list). Tests run with the offscreen platform.

## Behaviour to keep

* Git runs with `--literal-pathspecs`, `GIT_TERMINAL_PROMPT=0`, `GIT_EDITOR=true`, `GIT_MERGE_AUTOEDIT=no` and in a new session (`Setsid`), so it can't hang waiting on a terminal, and with `GIT_OPTIONAL_LOCKS=0`, so that its background reads don't get in the way of other git commands. `Setsid` is why this builds for Linux and macOS but not Windows.
* `Window.background` runs one changing command at a time off the main thread, with the actions disabled, then rescans. `Window.run` is that, telling of any failure; deleting a branch uses `background` itself, as a refusal from git becomes a question. Only quick reads that a dialog needs first (branches, remotes, a branch name's validity) run on the main thread. Rescans and diffs run in the background too, and an answer that isn't to the latest request is dropped.
* Status comes from `git status --porcelain=v2 --branch -z`. Unstaging always names paths, as a `git reset` without any would abandon a merge in progress. A status line's old path goes only on the side that renamed or copied the file (`sideOf`), as staging names it to git.
* Diffs are read up to `git.MaxDiff`, and nothing follows one that was cut off. All patches are asked for with `git.patchOptions`, which `diff.Parse` relies on. It drops each file's header (`diff`, `index`, `---`, `+++`, new and deleted file modes, similarity), keeping what is news (renames, mode changes, binary). In the history a bold file name replaces it (`diffView.titles`), which file jumping uses (`Parsed.Files`). It also makes sure the text has exactly one block per line, which `diffView.paint` relies on. A hunk's `@@` range is in the Hunk headers colour (`HunkColour`, Solarized's base0 grey by default) with no background, and any text after it is the normal colour.
* The default diff colours are Solarized's green, red and base0 grey (`DefaultAdded`, `DefaultRemoved`, `DefaultHunk`), as the change circles are. A colour saved that is still an old default (`oldDefaults`: #00a000, #ff1919, #808080) is taken as the new one, as it was never chosen.
* Diffs colour text, not backgrounds (the user's choice): added and removed lines take their colours as they are, through char formats (`diffView.paint`). Nothing in a diff has a background.
* The settings dialog is tabbed, with one tab so far, User interface (an Appearance section, then History, in the same form so that the fields line up, with how many commits are read at a time, then a Colours table of Name and Colour, as `../prism` has it, with bold section rows and a filled button for each colour). Code font is one row under Appearance, as `../apemail` has it: any font of the system (no monospaced filter: the user wants any), the size inline, and a Default button. The code's font and size (`CodeFont`, `CodeFontSize`) apply to both diffs and the commit message; empty or 0 follows the system's fixed width font.
* The about box's title is as apemail's (`newAboutTitle`): the name in bold at `titleScale`, with the version to its right on the same baseline at `versionScale` and `versionOpacity`, as the release it is or follows (`release`: v1.2.4-0.… is shown as v1.2.3), or dev. The box is fitted to the height its contents need at its width (`fitHeight`), as apemail's is, as Qt's own height leaves a gap above the licences.
* Themes: light and dark are Fusion with our own palette; following the system restores the desktop's style and an empty palette. `applyTheme` is not called at startup when following the system.
* Checkout offers every local branch, in order of name ignoring case (`byName`), the current one chosen (OK is disabled while it is, as there is nothing to do, and it is chosen again when a remote branch chosen goes from the list), and the remote ones after them, in order too, only while its Include remote branches checkbox is ticked (`newCheckoutDialog`, unticked to start with), keeping the branch chosen if it is still there. Ticking it the first time fetches (`git fetch --all`) in the background, with the list and OK disabled and Fetching… said, then lists the remote branches; a failed fetch says why and lists those already known. The dialog is marked `finished` once answered, so that a fetch ending later touches nothing, and a cancelled dialog that fetched rescans. A remote branch is checked out as a new local branch tracking it. Form dialogs' fields grow to the dialog's width (`AllNonFixedFieldsGrow`), as some styles keep them narrow, and the first field of text has the focus when one is shown (`formDialog.firstText`), as it would otherwise go to OK, made first, unless `formDialog.focus` names another: Checkout focuses its list of branches.
* Branch > Discard All Changes runs `git reset --hard HEAD` then `git clean -f -d` (`git.DiscardChanges`; `read-tree --empty` on a branch with no commits), keeping ignored files and commits, and abandoning a merge. It always asks first, No being the default, counting files put back and new files (untracked or newly staged) deleted. It is enabled only with something to discard, and not during a rebase, which has Abort Rebase.
* Force push is `--force-with-lease`, always asks first, and the Force push checkbox clears after a successful push. Only the Push buttons, the toolbar's and the one beside the message, honour the checkbox (`pushButton`): the Remote menu's Push, on Ctrl+P, never forces (the user's choice), and Force Push… there always does.
* The stage button stages everything listed, and is Unstage Changes when everything is staged (`allStaged`). The Stage Changes menu item only stages; Stage Selected and double-click stage only those chosen. Only one list has a selection at a time.
* A changed file in a list is its path with a circle for what happened to it (`changeIcon`), in place of git's letter: `changeDotSize` (12, as reghead's dots of its matches) wide, an outline in its colour and a wash of it (`changeFill`) inside, as apemail's folders are, in Solarized's accents (`changeColours`: blue modified, green added, red deleted, violet renamed, cyan copied, yellow type changed, orange in conflict, and its base0 grey untracked), the same in every theme (the user's choice), and kept on a selected row. Its tooltip says it in words (`explain`). The first row of the history's files, the message, has a blank of the same size.
* Pane headings are bold (`heading`), and splitter handles are made through `OnCreateHandle` to paint only a row of grip dots, as `../reghead` does (`newPaneSplitter`).
* The status bar has a size grip and all its text at the left, at 50% opacity: the branch, then the last message, in labels of their own (`Window.say`). Don't use `ShowMessage`, which hides widgets beside it, or `AddPermanentWidget`, which goes on the right.
* The history is like gitk: commits of HEAD above, in `--topo-order`, as the graph needs every commit before its parents, (read `pageSize` at a time, from the settings' `HistoryPageSize`: 500 by default, 50 to 10000, taking effect from the next read; more on scrolling to the end), the chosen commit's files beside its whole diff below. Choosing a file scrolls to its name in the diff, relying on `git diff-tree --name-status` and `-p` listing files in the same order. Merges are diffed against their first parent. It reads only while on show: a rescan marks it stale (`markHistoryStale`), and it reloads on being shown. Its panes get their sizes when first shown (`historyTab.sized`), and are saved only if they have been.
* While there is anything uncommitted, the first row of the history is a stand-in commit (`git.UncommittedCommit`), whose parent is HEAD so that the graph joins up. It is in `historyTab.list` but read commits are counted without it (`committed`). `CommitDetail` shows it as everything since HEAD plus untracked files. It changes without its row changing, so it is read again on every rescan, keeping its scroll position.
* The graph is a column of the commit list, painted by an item delegate (`graphColumn`) from `graph.Layout`'s rows: only rows on show are painted, and it scrolls with the list. The layout is fed a page at a time. Each row's bottom edges must meet the next row's top edges, which `TestRowsJoinUp` checks on random histories. Changing lanes is an S curve leaving and arriving upright, so that lines run on smoothly between rows. The column is as wide as the lanes need, up to `graphMost`. A first parent already waited for in a lane to the right doesn't step over to it: its own lane waits too, and they meet at the parent, in the leftmost, so the graph doesn't wander right (`TestDoesNotWanderRight`).
* Interactive rebase starts from a commit's context menu in the history (`commitMenu`), never the uncommitted row, and only on a clean work tree with no merge or rebase going. It covers that commit up to HEAD (`git.RebaseCommits`, which refuses a range holding a merge), and the dialog (`rebaseDialog`) edits the plan: a row per commit, oldest first, each with its own action combo of plain action names (an item widget; the wheel changes it only once it has focus, so that it scrolls the list; focusing or choosing in it makes its row the only one chosen (`chooseOnly`), so that the message below is that commit's). Below the list is only the chosen commit's message, full width, with no diff. The message is enabled only for a commit reworded, so that it is visibly greyed otherwise; Reword puts the cursor in it once the popup has closed (`editMessage`), and for a second after sends the focus back to it if it lands on the list or a combo (`reclaimFocus`), as on Wayland closing the popup puts the focus on the list later still. The dialog has no keyboard shortcuts (the user's choice). Rows are only dragged into order (`moved`). Qt only draws where a drag would go: the drop is handled in `dropAt` and ignored, so that Qt moves no rows, as it would delete the combos of rows it moved. Rows stay in place while the steps shown on them change. Qt delivers no drag events sent by hand, so tests call `dropAt`. The dialog's size is saved in the settings (`RebaseWidth`, `RebaseHeight`, 0 until first closed, when it opens at four fifths of the window) whenever it closes. Git is given the plan through `GIT_SEQUENCE_EDITOR`, a `cp` of a temporary file. Reword is a pick then an `exec` that amends with the new message, a line at a time through `printf`, each quoted for the shell (`git.todo`), as git would otherwise want an editor. Long messages are cut in the list (`subjectWidth`) and tooltips (`excerpt`), and shown whole in the message. A stop (`Status.Rebasing`, read from `rebase-merge` or `rebase-apply`) is told of by `Window.rebaseStep`, and handled from the Branch menu: Continue Rebase amends what is staged into a commit stopped at to edit, then continues. A dialog is marked `finished` before it is deleted, so that a timer firing late does nothing.
* In the file lists, ctrl and shift select several files. Dragging keeps one file selected, moving with the pointer, so each is shown in the diff in turn (`newFileList`).
* At the toolbar's right, beyond a space that takes up the rest, is a spinner (`spinner.go`): an arc turning, the size of a button's icon and in the icons' style, with Working under it, not a button. Every piece of background work calls `beginWork` before it goes and `endWork` first thing when it comes back, its answer used or dropped, so that they always pair (`TestWorkPairs`); Checkout's fetch does so from its goroutine through `mainthread`. The spinner shows only once work has gone on for `spinnerDelay`, so that quick work does not flicker, and goes when the count is back to 0.
* There are no tabs. Under the menus is a toolbar the size of apemail's (`makeToolBar`: 32 pixel icons, text under them, not movable, each button at least `toolButtonWidth` wide so that short names are not thin, and with no tooltips: Qt gives a button its action's name as one whatever is set, so an event filter takes the tooltip event). Push is a split button (`MenuButtonPopup`) whose own menu, not the Remote menu, has a checkable Force push option (`forceToggle`), ticked along with the Force push checkbox either way: while ticked, both Push buttons say Force Push and force (not Ctrl+P), and a successful push clears them all. Whether it is ticked is saved on closing (`ForcePush`) and ticked again on starting, once the window is joined up so that the option and buttons follow: New Branch, Checkout, Delete, a separator, Rescan, Stage, a separator, Pull, Push, a separator, History. Stage is `stageButton`, which both Stage buttons trigger: it unstages everything, as Unstage with a minus icon, when everything is staged (`allStaged`). Its buttons are the menus' own actions, with their icon text set to drop the ellipsis, so that they are enabled alike. History is a checkable action of its own, Show History in the Branch menu on Ctrl+H, that shows the history in place of the changes (`views`, a stacked widget; `setHistoryShown`, `historyShown`). The history is never shown by itself: it starts on the changes whatever the repository holds (the user's choice). The icons are drawn in code in apemail's style (`toolicons.go`: outlines on a grid of 24, 1.5 wide, round ends and joins, in the palette's text colour, disabled text where disabled, through an icon engine so that they follow the theme), so that Qt's SVG module is not needed.
* On starting, the repository opened is the one named on the command line, or else the one the current folder is in, or else none, waiting for File > Open Repository. The last one open is not remembered (the user's choice), and an older settings file's `repository` is ignored.
* Window size, maximized state and the three splitters are saved on close, and the rebase dialog's size when it closes. Pane sizes are applied after the window is shown.
* A window must not be deleted while a background command may still answer to it, so tests close windows without deleting them.
